# Запуск обучения и интернет-поиска

## Что делает приложение

1. Пользователь выбирает пас пяткой или удар через себя.
2. Поиск YouTube получает кандидатов. Четыре исходных видео датасета исключаются по ID.
3. Скачиваются первые 30–180 секунд каждого выбранного видео в разрешении до 480p.
4. Модель проверяет трёхсекундные окна с шагом в одну секунду. Последнее окно заканчивается у границы проверяемой записи.
5. Окно принимается, если выбранное действие — первый класс модели и его оценка превышает порог, подобранный по validation. Пересекающиеся срабатывания объединяются.
6. Страница показывает локальное видео, диапазон найденного фрагмента и ссылку с таймкодом на YouTube.

Название ролика не является подтверждением действия. Ошибки доступа и пустые результаты отображаются явно. Проверяется только выбранное начало ролика; остальная запись не считается просмотренной. Таймкод обозначает границы окна, а не точный момент касания мяча.

## Окружение

Нужен Python 3.12. Проверенная локальная связка: PyTorch 2.14.0+cpu, Torchvision 0.29.0+cpu. Из-за медленной загрузки CUDA для первого эксперимента использована CPU-версия. В текущем `.venv` доступны также библиотеки базового Python; глобальное окружение не изменялось. Команды ниже создают самостоятельное окружение на другой машине.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install torch==2.14.0 torchvision==0.29.0 --index-url https://download.pytorch.org/whl/cpu
.\.venv\Scripts\python.exe -m pip install -r requirements-ml.txt
```

Для GPU установите совместимую CUDA-сборку по [официальной инструкции PyTorch](https://pytorch.org/get-started/locally/) и проверьте `torch.cuda.is_available()`. Код обучения и анализа автоматически использует доступную CUDA, если не задан `--device cpu`. Brev не требуется для запуска локального прототипа.

## Обучение

```powershell
.\.venv\Scripts\python.exe -u -X utf8 -m socspot.train --run r3d18-v2 --splits data/splits/review_v2_source_holdout --epochs 8 --warmup-epochs 2 --batch-size 4 --device cpu
```

Для повторного эксперимента укажите новое имя `--run`: существующие веса и итоговые тестовые оценки не перезаписываются.

Обучение этой командой на [разметке v2](annotation-v2.md) завершено: 43/92 верных ответов на test (46,7%), macro F1 0,389. Это слабый результат, особенно для ударов через себя: 1/25. Подробности — в [отчёте v2](../data/reports/r3d18-v2/README.md). Сервис использует v2; веса v1 и прежняя оценка сохранены. Для повторного запуска выберите новое имя. Для воспроизведения v1 дополнительно укажите `--splits data/splits/initial_source_holdout`. Кеш кадров зависит от SHA-256 видео, поэтому изменённые клипы получают новые записи кеша.

Начальная модель — [R3D-18 с весами Kinetics-400](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.video.r3d_18.html). Первые две эпохи обучают классификатор из трёх классов, затем размораживается `layer4`. Остальная модель и статистики BatchNorm остаются фиксированными. AdamW использует learning rate 0,001 для классификатора и 0,0001 для `layer4`, а веса классов вычисляются только по train. При наличии CUDA используется mixed precision.

Из каждого клипа равномерно берутся 16 кадров по всей его длине. Это отличается от исходной частоты 15 FPS модели Kinetics: здесь сохраняется контекст трёхсекундного действия. Кадры приводятся к 128×171, затем к 112×112. На train применяется единый для всех кадров случайный кроп и горизонтальное отражение; validation, test и поиск используют центральный кроп. Нормализация соответствует исходным весам. Размеченное время действия при предсказании не используется.

Лучшая эпоха выбирается по macro F1 на validation, при равенстве — по loss. Пороги действий выбираются по F0.5 на той же validation, с предпочтением precision. Test используется после выбора весов и порогов. Поэтому при дальнейшей настройке по уже увиденному test его оценку нельзя продолжать считать независимой.

Результаты:

- `models/<run>/best.pt`: локальные веса, классы, преобразования, пороги и хеши разбиения.
- `models/current.json`: модель, которую использует сервис; появляется после успешного окончания обучения и оценки.
- `data/reports/<run>/config.json`: параметры и версии библиотек.
- `data/reports/<run>/history.json`: история эпох.
- `data/reports/<run>/report.json`: precision, recall, F1, accuracy и матрица ошибок на test.
- `data/reports/<run>/test_predictions.json`: ответы по каждому тестовому клипу, включая ошибки.

Веса, кеш кадров и скачанные интернет-видео исключены из Git. JSON-отчёты сохраняются в репозитории. Исходная разметка и разбиение не меняются при обучении.

## Страница поиска

```powershell
.\scripts\start-search.ps1
```

Откройте <http://127.0.0.1:8767>. Сервер слушает только локальный адрес. Одновременно обрабатывается один поиск, максимум пять видео, до трёх минут каждого. Можно отменить задачу; выполняющаяся загрузка заканчивается или достигает таймаута, а анализ останавливается между окнами. После перезапуска сервера незавершённая задача получает статус `interrupted`.

По умолчанию используется поиск [yt-dlp](https://github.com/yt-dlp/yt-dlp), без ключа и чтения cookies браузера. Для JavaScript-проверок YouTube нужен Node.js и установленный `yt-dlp-ejs`. Если задана переменная `YOUTUBE_API_KEY`, поиск кандидатов использует [YouTube Data API](https://developers.google.com/youtube/v3/docs/search/list); получение видео остаётся отдельным этапом. Ключ не сохраняется в результатах.

YouTube может изменить выдачу, ограничить загрузку или потребовать вход. Такое видео получает ошибку, а не вымышленную оценку. Исходники и результаты кешируются в `data/search/`, новые ролики автоматически в обучение не добавляются.

CLI для проверки:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m socspot.search backheel_pass --limit 1 --seconds 30
.\.venv\Scripts\python.exe -X utf8 -m socspot.search bicycle_kick --limit 3 --discover-only
```

## API для Spring Boot или другого клиента

Spring Boot в этом репозитории пока отсутствует. Python-сервис предоставляет готовую HTTP-границу:

| Запрос | Результат |
|---|---|
| `GET /api/health` | Готовность модели и ID активной задачи |
| `GET /api/model` | Отчёт по активной модели |
| `POST /api/search` | `202` и фоновая задача; тело: `{"action":"backheel_pass","limit":3,"seconds":60}` |
| `GET /api/jobs/{id}` | Состояние, фактический прогресс, результаты и ошибки |
| `POST /api/jobs/{id}/cancel` | Запрос отмены |
| `GET /api/jobs/{id}/video/{video_id}` | Видео для локального предпросмотра, с поддержкой Range |

При занятом обработчике возвращается `409`, при отсутствии модели — `503`. Некорректный класс или превышение лимита возвращает `422`. Для работы Spring Boot достаточно создавать задачу, опрашивать её статус и передавать `results` своему интерфейсу.

## Границы качества

Первый эксперимент использовал предварительные метки: 185 train, 44 validation, 78 test. Для v2 подготовлены 204 / 49 / 92 клипа; тест уже известен по первому эксперименту. Невыявленные повторы между сборниками и совпадения матчей ещё возможны. Большая часть `other` происходит из HF и отличается частотой кадров и оформлением: модель может запоминать источник. Проверка коротких отобранных клипов не измеряет полноту поиска в длинной записи, а оценки softmax не откалиброваны как вероятности. Для следующей независимой оценки нужны полностью размеченные новые записи с целевыми событиями и обычной игрой.

Дополнение [infactory-ai/soccer-events](https://huggingface.co/datasets/infactory-ai/soccer-events) предназначено для некоммерческого исследовательского использования; первый эксперимент сохраняет это ограничение.

Проверки кода: `python -m pytest tests -q`. Реальный поиск и воспроизведение проверяются отдельно от этих тестов.
